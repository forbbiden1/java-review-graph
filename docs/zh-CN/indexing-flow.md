# 索引流程

## 目的

本文档定义图谱如何构建，以及源码变更后如何刷新。

## 全量索引

```text
项目导入
  -> 识别构建工具和模块
  -> 解析源码根目录和 classpath
  -> 使用带绑定的 JDT 解析 Java 文件
  -> 抽取符号
  -> 抽取关系
  -> 计算 hash
  -> 持久化快照
```

## 增量索引

```text
变更文件列表
  -> 分类变更文件
  -> 识别 rename / move 对，并在诊断信息里同时保留旧路径和新路径
  -> 如果没有基线快照或构建元数据变化，则回退到全量扫描
  -> 基于上一份快照的关系，把一跳关联的 Java 文件也加入重建集合
  -> 只分析需要重建的文件集合
  -> 复用上一份快照中未变化的文件、符号和关系
  -> 从组装后的新快照中移除已删除文件
  -> 对比旧快照与新快照
  -> 推导一跳受影响符号，并覆盖“删除邻居”场景
  -> 发布新的 review 快照
```

## 变更来源

- 手工传入文件列表
- 基于最新快照 commit 到当前工作区的 git diff
- 文件监听事件

## Git 自动增量模式

- 如果最新快照保存了 Git commit，就把它作为 diff 基线
- 收集这个基线之后已经提交的文件变化
- 追加当前 `git diff HEAD` 中的未提交变化
- 追加 `git ls-files --others --exclude-standard` 中的未跟踪文件
- 如果最新快照没有可用的提交基线，则退回为当前工作区变更集合

## 文件分类

### Java 源码变更

先规范化变更的 `.java` 路径，重建这些文件，再把上一份快照里与其一跳关联的文件一起纳入重建。
如果变更的 Java 文件已经被删除，则从新快照中移除它的旧记录，并尽量重建仍然存活的一跳邻居。

### 构建文件变更

如果 `pom.xml`、`build.gradle` 或模块设置发生变化，会直接回退到全量扫描，因为项目模型可能已经变化。

### 资源文件变更

MVP 默认不重新跑分析，而是复用上一份快照的数据并持久化一条新的快照边界。除非后续增加资源到代码的关系支持。

## 快照 Diff 规则

Diff 基于稳定的 `symbol_key`。

- 只在新快照中存在：`added`
- 只在旧快照中存在：`deleted`
- `api_hash` 变化：`modified_api`
- 只有 `impl_hash` 变化：`modified_impl`
- 自身没变但邻接目标发生变化：`impacted`

## 影响传播规则

### 方法变化

- 变更方法自身标为 `modified_api` 或 `modified_impl`
- 直接调用方标为 `impacted`
- 所属类型标为 changed
- 调用方所属类型标为 `impacted`

### 类型变化

- 变更类型自身标为 `modified_api` 或 `modified_impl`
- 直接使用它的类型标为 `impacted`
- 已删除类型的直接邻居也会标为 `impacted`
- 子类和覆盖方法也可能被标记为 `impacted`

## 当前简化策略

MVP 的影响模型刻意保持浅层：

- 先做一跳调用方传播
- 先做一跳类型使用方传播
- 更深层传播后续通过显式深度配置再加
