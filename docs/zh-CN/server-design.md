# 服务端设计

## 目的

`apps/server` 是本地后端，负责项目导入、索引控制、快照持久化和图查询。
当前持久化目标是本地 SQLite 数据库文件。

## 职责

- 管理项目元数据
- 触发全量和增量索引
- 持久化快照、符号、关系和变更记录
- 提供图查询和 review API
- 把分析器输出转换成适合查询的响应结构

## 分层

- `api`
  控制器以及请求或响应 DTO
- `application`
  用例编排和流程协调
- `domain`
  后端侧领域模型
- `infrastructure`
  持久化、文件访问和分析器集成适配

当前 `application` 层的职责拆分：

- `ProjectIndexService`
  顶层索引用例编排
- `IncrementalPlanner`
  变更文件解析、增量回退规则和重建范围规划
- `SnapshotAssembler`
  把本次重建结果和旧快照中的未变化状态组装成新快照
- `ChangeStatusCalculator`
  计算 symbol diff 状态和受影响符号
- `ReviewQueryService`
  面向快照的图查询组装，以及针对类图和方法图的定向关系读取
- `ChangeSetReviewService`
  基于单个快照和一组 Git 或手动变更文件生成面向 review 的变更摘要

## 主要用例

### 项目导入

- 注册本地仓库路径
- 检测构建工具
- 创建初始项目记录

第一批真正落地的服务端能力应当覆盖：

- 在 SQLite 中插入或复用项目记录
- 查询已导入项目列表
- 按 id 查询单个项目

### 全量索引

- 构建项目描述对象
- 调用分析器
- 持久化快照和图状态

### 增量索引

- 接收变更文件列表或 Git 自动 diff 输入
- 在存在历史快照时，以最新快照作为增量基线
- 支持 `changeSource = git|manual`，默认使用 `git`
- 重建变更的 Java 文件，以及上一份快照中与其一跳关联的文件
- 复用基线快照中未变化的文件、符号和关系
- 如果构建元数据变化或没有基线快照，则回退到全量扫描
- 持久化组装后的快照和变更集
- 计算一跳受影响符号摘要

### 图查询

- 类图
- 类详情
- 单类方法图
- 变更符号列表
- 影响范围
- 变更集 review 摘要

当前查询链路的行为：

- 类图只读取选定快照中的 `EXTENDS`、`IMPLEMENTS` 和 `USES_TYPE` 关系，并进一步裁剪为已索引类型之间的边
- 方法图只读取 `CALLS` 关系，且源和目标都必须属于当前类的方法集合
- 变更集 review 会结合单个快照与一组 Git 或手动变更文件，把文件路径映射到变更符号和已持久化的受影响符号
- 变更集 review 还会基于变更状态、受影响数量和删除符号信号，生成一份确定性的风险摘要
- 变更集 review 还可以直接渲染一份可导出的 Markdown 报告，且不会引入 AI 或非确定性评分
- 当较窄的关系切片已经足够时，查询接口不会再先加载整份快照的全部关系再做内存过滤

## 持久化方向

后端需要存储：

- 项目和快照元数据
- 规范化后的 symbol 记录
- 规范化后的 relation 记录
- 显式的 symbol change 记录

后端不应该依赖前端图布局引擎。

## SQLite 决策

- 数据库引擎：SQLite
- 默认数据库路径：`./data/java-review-graph.db`
- 初始化方式：Spring 启动时执行 SQL 初始化
- 当前访问方式：以 JDBC 为中心的本地持久化

之所以默认使用 SQLite，是因为当前产品是本地优先、单用户使用场景。
如果后续出现多用户或远程部署需求，再重新评估持久化抽象。

## MVP 规则

API 响应应当围绕 review 任务组织，而不是直接暴露底层存储结构。
优先提供“仅变更视图”和“局部方法展开”这类直接可用的接口。
