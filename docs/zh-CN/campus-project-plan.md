# 校招项目规划

## 项目定位

Java Review Graph 可以定位为：

`一个面向 Java 项目的本地代码审查与变更影响分析工具`

这个定位比通用代码浏览器更强，因为它同时覆盖了：

- 静态分析
- 基于快照的变更跟踪
- 图查询与可视化
- 面向 review 的风险和影响解释

如果作为校招项目，应该重点强调：

- 真实工程场景，而不是演示型 CRUD
- 清晰的分析器、后端、存储、前端分层
- 输出的是可解释的 review 结果，而不只是图谱原始数据
- 从 Git 变更到 review 结果的完整端到端流程

## 高价值展示功能

### 1. Git commit / PR 影响分析

目标：

- 接收一个 commit 区间、分支 diff 或 patch 类变更集
- 把变更文件映射到变更符号
- 推导受影响的类和方法
- 为该变更集生成 review 摘要

预期输出：

- 变更文件
- 变更符号
- 受影响符号
- 受影响调用链
- 建议重点 review 的位置

价值：

- 最贴近真实代码审查流程
- 很适合在面试中短时间演示
- 能把分析器、快照 diff、图查询和 UI 串成一条线

### 2. 变更风险评分

目标：

- 对一次变更打出低 / 中 / 高风险分数
- 用清晰规则解释分数来源

可用信号：

- 是否修改了公共 API
- 是否修改了高扇出符号
- 是否发生跨模块传播
- 是否触达核心入口或共享工具类
- 是否影响更深层调用链

价值：

- 展示的不只是可视化，而是图谱推理能力
- 很容易讲出“工程价值 + 可解释性”的故事

### 3. 调用路径与依赖路径分析

目标：

- 支持两个符号之间的最短路径或限定深度路径查询
- 回答“谁依赖了这个类”和“这次改动如何传播”

预期查询：

- 从源符号到目标符号的路径
- 某个符号的上游依赖者
- 从一个变更符号向下游传播的影响路径

价值：

- 能直接体现图算法价值
- 演示效果很强

### 4. 历史快照对比

目标：

- 比较任意两个快照
- 解释新增、删除、更新的符号和关系
- 展示结构随时间的演进

预期输出：

- 符号 diff 摘要
- 关系 diff 摘要
- 某个类或包的演进时间线

价值：

- 把项目从“看当前图谱”提升成“看代码结构演化”

### 5. 审查报告导出

目标：

- 先导出 Markdown，再可选扩展到 HTML / PDF

建议内容：

- 变更摘要
- 受影响图谱片段
- 风险等级与解释
- 建议回归范围

价值：

- 让项目更像可落地工具，而不是只在页面上演示

### 6. AI 辅助解释

目标：

- 以已有的图谱和 diff 结果作为结构化输入
- 生成简洁的 review 说明和测试建议

边界：

- AI 负责总结分析结果
- AI 不替代核心图谱推导过程

价值：

- 增加现代感，但不会削弱技术深度
- 很适合包装成“静态分析 + 图谱 + AI”的项目叙事

## 推荐开发顺序

如果目标是把项目优化成校招作品，建议优先顺序为：

1. Git commit / PR 影响分析
2. 变更风险评分
3. 审查报告导出
4. 调用路径分析
5. 历史快照对比
6. AI 辅助解释

前 3 项做完，就已经是一版很强的面试展示版本。

## 粗略开发计划

## 阶段 1：变更集 review 工作流

范围：

- 选择 commit 区间或 Git diff 基线
- 生成变更符号和受影响符号摘要
- 在 UI 中展示面向 review 的变更视图
- 提供变更集分析 API

主要交付：

- `POST /api/projects/{projectId}/review/change-set`
- 桌面端和 Web 端的变更摘要面板
- 持久化的变更集分析结果或派生快照视图

演示价值：

- 导入项目
- 选择一个 commit 区间
- 立即展示受影响图谱和 review 目标

## 阶段 2：风险和路径推理

范围：

- 增加风险评分规则
- 增加符号路径查询
- 解释为什么这次改动有风险

主要交付：

- 风险评分 API 与规则模型
- 路径查询 API
- UI 风险标记和解释面板

演示价值：

- 点击一个变更类
- 展示传播路径和风险解释

## 阶段 3：报告导出与作品打磨

范围：

- 导出 Markdown 报告
- 增加快照对快照的对比摘要
- 打磨演示场景下的展示体验

主要交付：

- 报告导出功能
- 快照对比视图
- 更完整的空状态、加载状态和 demo 数据

演示价值：

- 一次分析完成后可直接导出一份可分享报告

## 阶段 4：AI 解释层

范围：

- 把结构化图谱结论转成可读的 review 建议
- 基于风险和路径结果生成测试关注建议

主要交付：

- 基于变更摘要和图谱证据的 prompt 输入模型
- 带证据引用的 AI 说明面板

演示价值：

- 在传统静态分析之上叠加 AI 解释层

## 实施注意事项

- 核心推理优先保持确定性。
- 把 AI 视为图谱证据之上的展示和解释层。
- 每个风险结论都应该能回溯到存储信号或图路径。
- 继续保持本地优先作为默认体验。

## 面试演示建议

- 选择一个真实 Java 项目，而不是刻意造的小玩具仓库。
- 演示一条完整链路：导入项目 -> 建索引 -> 选择变更集 -> 查看影响 -> 导出报告。
- 准备 2 到 3 条具体风险规则，并说明为什么有用。
- 面试时能清楚讲明分析器、后端、SQLite、前端之间的职责拆分。
